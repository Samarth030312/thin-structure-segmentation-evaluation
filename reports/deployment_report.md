# Deployment Report — PyTorch vs ONNX Runtime vs TensorRT

> Perception is only useful if it runs on the vehicle/UAV. This report covers the
> full deployment track: TorchScript/ONNX export with verified numerical parity,
> a PyTorch-vs-ONNX-Runtime latency comparison (measured), and the TensorRT path
> for Jetson-class hardware (documented; runtime not present here).
> Generated by `scripts/export_model.py` + `scripts/run_deploy_benchmark.py`.

## 1. Export pipeline (verified)

```
PyTorch ckpt ──export_model.py──► TorchScript (.ts.pt)  ──► LibTorch C++ (deploy/cpp)
                               └─► ONNX (.onnx)          ──► ONNX Runtime / TensorRT
```
- **TorchScript reload parity:** `max|Δ| = 0.00e+00` (bit-exact) — verified at export.
- **ONNX parity vs PyTorch:** `max|Δ| = 8.9e-08` (fp32 round-off) — numerically identical.

## 2. Measured: PyTorch vs ONNX Runtime (MiniUNet, 256², CPU, batch 1)

| Backend | Latency (ms) | FPS | Parity vs PyTorch | Speedup |
|---|---|---|---|---|
| PyTorch (eager) | 170.6 | 5.9 | — | 1.00× |
| **ONNX Runtime** | **116.1** | **8.6** | 8.9e-08 | **1.47×** |
| TensorRT (FP16) | — | — | — | *2-4× typical (see §4)* |

**Finding:** ONNX Runtime's graph optimisations (operator fusion, constant
folding) give a **1.47× CPU speedup at identical accuracy** with zero code in the
inference loop — free latency. The graph is portable to mobile/embedded runtimes.

> GPU-backend and full-model (U-Net/SegFormer) numbers are produced by the same
> script with `--device cuda --model segformer`; run when the GPU is free of
> training. The accuracy/latency Pareto front is in `leaderboard_performance.csv`.

## 3. C++/LibTorch engine

`deploy/cpp/` is a complete LibTorch inference engine (122 LOC) with
train/deploy-parity preprocessing (resize→RGB→ImageNet-norm→CHW), on-device
argmax, and FPS reporting. Build: `cmake -DCMAKE_PREFIX_PATH=/path/to/libtorch ..`
(see `deploy/README.md`). CI syntax-checks the translation unit.

## 4. TensorRT path (Jetson-class deployment)

```bash
# FP16 engine:
trtexec --onnx=deploy/models/<model>.onnx --saveEngine=<model>_fp16.engine --fp16
# INT8 (calibrate on ~300 representative frames) typically halves latency again:
trtexec --onnx=... --int8 --calib=<cache>
```
The ONNX export uses **dynamic H/W axes**, so one engine serves multiple UAV
altitudes/resolutions. On Orin-class hardware, FP16 TensorRT on an efficient
backbone (SegFormer-B0 / U-Net-R18) is the recommended real-time configuration.

## 5. Deployment recommendation (ties to the architecture study)

| Target | Model | Backend | Rationale |
|---|---|---|---|
| **Cloud / offline mapping** | U-Net++ + CoRe | PyTorch/ONNX GPU | max accuracy & topology |
| **On-board UAV (Orin)** | SegFormer-B0 + CoRe | **TensorRT FP16** | 3.7 M params, best accuracy/latency |
| **Edge CPU / fallback** | MiniUNet / U-Net-R18 | ONNX Runtime | 1.47× CPU speedup, no GPU needed |

Deployment is a **Pareto decision** — `leaderboard_performance.csv` (params,
FLOPs, FPS, VRAM) is the artifact that drives it, not accuracy alone.
